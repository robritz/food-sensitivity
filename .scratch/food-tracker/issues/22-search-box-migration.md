# 22 — Migrate location search to Mapbox's Search Box API

**What to build:** Ticket 21's Place-field picklist searched Mapbox's classic Geocoding API with `types=poi,address`. Searching "starbucks" returned no results; live-testing against this account's actual Mapbox token (via curl, read-only) found `types=poi` returns **zero results for every query tested** -- "starbucks", "mcdonalds", "walmart", even "eiffel tower". This account's classic Geocoding endpoint has no business/landmark POI data at all; "starbucks" only ever matched literal street names like "Starbucks Drive Thru". Two earlier fix attempts (radius tuning, then a `bbox` hard-filter) didn't address this, because the actual defect was upstream of both: the API has no POI data to filter or bias in the first place.

Mapbox's newer Search Box API (`search/searchbox/v1/suggest` + `/retrieve`) does have real POI data -- live-tested and confirmed it returns real nearby businesses with coordinates, and also handles plain street addresses fine. This ticket migrates the Place-field picklist to it.

**Blocked by:** 21 (Location typeahead: nearby address suggestions while typing)

**Status:** done -- implemented on `fix/22-search-box-migration` (branched from `feature/21-location-typeahead-suggestions`)

- [x] The Place-field picklist searches Mapbox's Search Box API instead of the classic Geocoding API, so business/POI names actually resolve to real results
- [x] Results are biased toward the caregiver's current GPS position via `proximity`, and hard-restricted to within 5 miles via `bbox` -- verified live that Search Box's `bbox` is a genuine geo-filter (correctly returns 0 for a rural test point with no real nearby match, and real nearby results for a dense one), unlike the classic API's `bbox` (ticket 21's second fix attempt), which filters an already geography-blind candidate list and silently empties out for common queries
- [x] Results are restricted to `poi,address` types, same intent as ticket 21
- [x] Each suggestion shows a full-address subtitle (`placeName`), same as ticket 21
- [x] The search request is skipped while offline, same as ticket 21
- [x] **Behavior change, confirmed with the requester:** typed-but-unpicked text no longer silently resolves to coordinates in the background. Search Box's `/suggest` (the picklist search) doesn't return coordinates -- only `/retrieve` (called when a suggestion is actually picked) does. Requiring a pick matches how Search Box is meant to be used, and since Search Box also matches plain addresses, most real places (business or address) now show up to pick anyway. If nothing is picked, the entry still saves with just a name and no coordinates -- the same degrade path already used when GPS is unavailable.
- [x] No Mapbox token, no network, or a failed/empty search/retrieve all degrade gracefully -- never blocks entry submission

**Implementation notes:**

- `data-access/src/mapboxSearchClient.ts` (new): isolated HTTP calls to Search Box's `/suggest` and `/retrieve`, mirroring `mapboxClient.ts`'s isolation convention (network-touching code kept separate from fallback-on-failure logic, for unit-testability). `fetchPlaceSuggestions(query, token, sessionToken, options)` returns `PlaceSuggestion[]` (`{ mapboxId, name, placeName }` -- no coordinates). `fetchPlaceDetails(mapboxId, token, sessionToken)` returns `PlaceDetails | null` (`PlaceSuggestion` + `latitude`/`longitude`). Both require a caller-supplied `sessionToken` -- Mapbox bills a suggest→retrieve pair sharing one token as a single session. `PlaceSuggestOptions.radiusMiles` converts to a `bbox` around `proximity` (same miles-per-degree-latitude math ticket 21's second attempt briefly had in `mapboxClient.ts` -- reintroduced here now that it's verified safe against this API).
- `data-access/src/locations.ts`: new `searchPlaces`/`retrievePlace` wrappers, same try/catch-to-empty/null pattern as `reverseGeocode`/the old `forwardGeocode`. The old `forwardGeocode`/`fetchForwardGeocode` (and `ForwardGeocodeMatch`/`ForwardGeocodeOptions`) are deleted -- `LogPage.tsx` was their only caller, so once it moved to `searchPlaces`/`retrievePlace` they were dead code (matches this branch's own precedent of deleting `debounce.ts` when its only call site went away). `fetchReverseGeocode`/`reverseGeocode` (classic API, the initial GPS→name suggestion on page load) are untouched -- no reported bug there, out of scope.
- `src/pages/LogPage.tsx`: `LocationSuggestion.latitude`/`longitude` are now optional -- a freshly-picked Search Box suggestion has neither until retrieved; the initial GPS-based suggestion (built from `reverseGeocode`, unchanged) still has both immediately. The "sync `locationCoords` from `locationPicker.value`" effect branches: if the picked value already has coordinates, use them directly; otherwise call `retrievePlace`, then patch the value via `setValue({ ...value, latitude, longitude, placeName })` (which re-triggers the same effect, now with coordinates present, terminating after one more no-op pass) and set `locationCoords`. A `locationRetrieveLoading` state drives a "Getting location details…" helper-text state, following the existing `locationSearchLoading`/`locationStatus === 'geocoding'` pattern.
- `locationSearchSessionTokenRef` (a ref, not state): lazily created via `crypto.randomUUID()` (this codebase's existing convention -- see the offline-queue id generation earlier in the same file) the first time a search fires after being empty, reused across keystrokes within that typing burst, and cleared back to `null` once a `retrieve` resolves (pick) or the query is cleared -- one UUID per suggest→retrieve session.
- Since Search Box's `bbox` is a real filter (verified), the picklist search now requests `LOCATION_SUGGESTION_LIMIT` (5) directly with no client-side distance re-filtering -- ticket 21's `LOCATION_SEARCH_FETCH_LIMIT`/`isWithinMiles` workaround (needed only because the classic API's `bbox` was unreliable) is gone, and so is the `isWithinMiles`/`geoDistance.ts` import from `LogPage.tsx` (still used by `MapPage.tsx` for its own radius filter, untouched).
- Verification: `data-access/test/mapboxSearchClient.test.ts` (new, mocked-fetch, mirrors `mapboxClient.test.ts`'s conventions) covers suggest's param assembly (session_token, proximity, bbox-from-radiusMiles, types, limit) and response mapping, and retrieve's URL/response mapping and null-on-no-feature. All 134 `data-access` tests pass, typecheck/build/lint all pass. **Also live-smoke-tested the actual compiled code** (not just hand-rolled curl) against the real Mapbox account: built `data-access`, then called the compiled `fetchPlaceSuggestions`/`fetchPlaceDetails` directly with the local `VITE_MAPBOX_TOKEN` -- confirmed 5 real nearby Starbucks locations with names/addresses from suggest, and real coordinates from retrieve on the top result.
- Manual browser check (the actual MUI Autocomplete/picklist UX, retrieve-loading state, session-token lifecycle across real typing/picking) is still unverified -- same tooling gap noted on tickets 18-21 (no browser-automation tool this session).
